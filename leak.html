Case 1

The two columns that rebuilt my label

The problem

I was building a classifier on FlyRank's search warehouse to flag which client sites were about to lose visibility. The label is a threshold: a client is positive at month M if, at month M+1, the share of their tracked queries that still return data falls below 0.6.

The first version scored 0.91 ROC AUC. That is where I stopped, because 0.91 is not a plausible score on this problem. Search visibility moves for reasons that are not in my data at all, including things the client does to their own site without telling anyone. A model that confident is usually a model that has been told the answer.

What I did

I went through all 34 features one at a time and asked each one a single question: could the value in this column have been written after the outcome I am trying to predict?

Most were fine. Two were not, and neither was obvious. The label is a ratio thresholded at 0.6. One of my features was the numerator of that ratio. Another was the denominator. They sat in different tables, under different names, computed by different jobs, and I had added them three weeks apart.

Individually, both are defensible. A month-M query count is a legitimate month-M feature. Together, over a window that touched M+1, they reconstruct the exact quantity the label is a threshold on. The model was not predicting the drop. It was reading it.

The decision

The easy fix is to delete those two column names and move on. I did not do that, and this is the part of the case I would defend hardest.

A blacklist of two names protects you from those two names. The next feature someone adds, or that I add in a month when I have forgotten this, can rebuild the same ratio out of different columns. The failure was never about the names.

So I wrote the rule as a time rule instead: no feature may be computed from any window that overlaps the outcome window, whatever it is called and whatever table it lives in. Then I applied that rule to all 34 columns rather than just to the two I had caught. It cost me four more features I liked, on top of the two that started it.

The rule is the deliverable here, not the fix. It still holds for features that did not exist when I wrote it, which a blacklist cannot do.

The part I could have quietly dropped

While checking the columns I also checked the population filter, which is the step people skip because it does not look like a feature question.

It was not clean. The rows I was keeping had been selected using a minimum-activity threshold that reads from the outcome window. That does not make the model worthless and it is not the same class of problem as the ratio pair, but it does mean my evaluation population was chosen with information the model does not get at prediction time.

I could have said nothing. Nobody had asked, and the numbers below would look the same. It is written into the notebook and into this page instead, because a caveat a reader finds themselves costs more than a caveat you hand them.

Base rate is 0.19, so the 0.42 PR AUC on the honest feature set is a little over twice chance. All three rows are the same model, the same rows, and the same random 5-fold split, so the only thing changing is the feature set.

Seven points of ROC AUC and 24 points of PR AUC went away. That is the result. The 0.84 is the number I report, and the 0.91 stays on the page because a reader who cannot see what I removed has no way to judge whether I removed enough.

One more thing this bought me that the table does not show. The four extra features the window rule killed were never flagged by anything except the rule. If I had only deleted the pair I found by hand, four leaky columns would still be in the model and it would still score 0.87, and I would have believed it.
